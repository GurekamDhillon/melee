# Rust port: inventory (2026-10-21)

Scope: what C the game is made of, how it is built today, what breaks when it is compiled as
ordinary native x86_64, where the assembly is, and how to cut the port into groups.
Everything below was measured in this worktree; the commands are listed at the end.

Not part of the game binary, so dead on PC:

- **src/MetroTRK** (20 files, 4.9k lines): the debugger stub. Not compiled at all. Drop.
- **src/Runtime** (7 files, 1.2k): no `.c` here is compiled. `platform.h` (macros:
  `STATIC_ASSERT`, `ASSERT_SIZE`...) is used as a header. Drop the code and keep the macros' meaning.
- **src/MSL** (23 files, 3.8k): used as the libc *headers* (`-nostdinc -isystem src/MSL`) plus
  `ansi_files.c` and `float.c`. `math_ppc.h` is force-included everywhere and **is not
  replaceable by Rust std**: its `sqrtf` and friends are Newton-Raphson on `__frsqrte` (see
  pc/gameworld/gekko_fp.c), and results feed physics. Port those as Rust functions with the
  same operation order; everything else in MSL becomes Rust core.
- **libs/dolphin**: only `mtx44.c` and `THPDec.c` are compiled; the paired-single `mtx`,
  `mtxvec`, `psmtx`, `vec` are replaced by `pc/gameworld/mtx_pc.c` (C reference routines,
  operand grouping preserved). The rest of the SDK is provided by `pc/platform` shims.
- **pc/platform** (87 files, 128k lines incl. headers): the native side (GX->Aurora, OS, PAD,
  CARD, DVD, AX, netplay, rollback, scripting, the m-ex interpreter). Not a group tonight.
  About 2,000 `gw_r*/gw_w*` guest-memory accessors live here (918 `gw_r32`, 482 `gw_w32`, 214
  `gw_rf32`...); **none are in game TUs**. In the native design each becomes a plain field
  access, which is the bulk of the pc/platform conversion work.

## 2. How the build compiles game TUs today

`tools/port/build.sh` -> `build_objects.py game` -> `_build/masstest/pipe_win.sh` per TU:

```
clang --target=ppc32-none-eabi -std=c99 -nostdinc -fno-builtin -DLINT -DTARGET_PC
  -fno-short-enums -fsigned-char -mlong-double-64 -fno-strict-aliasing -fwrapv -fcommon -fgnu89-inline
  -ftrivial-auto-var-init=zero -O2 -Xclang -disable-llvm-passes -emit-llvm -c -w
  -Isrc -Ipc -Ipc/gameworld -isystem src/MSL -isystem libs/dolphin/include -isystem libs/dolphin/src
  -isystem build/GALE01/include -include src/MSL/math_ppc.h  <tu> -o <tu>.bc
gwtool <tu>.bc -o <tu>.obj --imports=...      # retarget PPC IR -> i686, byte-swap every access, gw_ prefix
```

Shims (pc/platform) are compiled natively by `portlib.sh`: `clang --target=i686-pc-windows-msvc
-c -O2 -DTARGET_PC` + Aurora/SDL/Dawn/ENet includes. The link then regenerates
`gw_mex_bridge.c` (guest address -> native function) until a fixpoint; that whole mechanism
goes away in a native build (it only exists for m-ex code; the future importer replaces it).

`build/GALE01/include/sysdolphin/baselib/{debug_font,sislib_font}.inc` are generated by the
decomp's configure step and are not in this worktree; for the checks below I pointed
`-isystem` at the main checkout's copy (read-only). Do not commit them.

### Native x86_64 compile database

`docs/rust-port/gen_compile_commands.py` writes `compile_commands.json` for all 993 TUs with the
same flags but `--target=x86_64-pc-windows-msvc`, no `-mlong-double-64`/`-disable-llvm-passes`/
gwtool, and `-ffp-contract=off -fno-fast-math` added. The generated file is
`docs/rust-port/compile_commands.x86_64.json` (paths absolute to this worktree; regenerate in
another checkout). This is for c2rust/clangd/layout tooling, not a working native build.

**What breaks natively (measured with `--check`, `-fsyntax-only`):**

1. Unmasked: **all 993 TUs fail**, for two reasons only:
   - `src/MSL/stddef.h` `typedef unsigned long size_t` clashes with clang's 64-bit `size_t`
     (`unsigned long` is 32-bit under LLP64). Every TU.
   - **104 distinct `sizeof` layout assertions fail** (198 `ASSERT_SIZE` + 35 `STATIC_ASSERT` in the
     tree), because pointers are 8 bytes: `HSD_ObjAllocData` 0x2C, `HitCapsule` 0x138,
     `ColorOverlay` 0x80, `gmm_x0` 0x10A30, `lb_804D63A0_t` 0xBE00... Full list:
     `docs/rust-port/native_layout_asserts.txt`.
2. With those masked (`--mask-asserts`): **0 of 993 fail.** The C is otherwise native-clean as
   far as the parser is concerned. Warnings that mark real 64-bit hazards:
   319 `-Wpointer-to-int-cast`, 225 `-Wint-to-pointer-cast`, 91 `-Wvoid-pointer-to-int-cast`,
   49 `-Wint-to-void-pointer-cast`, 94 `-Wshorten-64-to-32` (684 pointer/int casts in 118 files).
   Hotspots: lb/lbmemory.c 47, ty/tydisplay.c 45, baselib/generator.c 44, gr/grcastle.c 33,
   baselib/particle.c 24, ftCo_0A01.c 21, gr/grhomerun.c 21, baselib/debugconsole_main.c 21,
   ty/tyfigupon.c 19, gr/grzebes.c 18, baselib/leak.c 18, pc/geno/geno_game.c 18, hsd_3A76.c 17,
   mp/mplib.c 16. Mostly pointers stored in `u32`/`s32` fields or compared as integers.
   Also 42 `-Wreturn-type` (non-void functions falling off the end: undefined behaviour the
   PPC build happens to get away with; each needs the value the PPC code returned, r3).

**Hazards the compiler does not flag** (these are the real native work, and why "native"
means rewriting data loading, not recompiling):

- **Big-endian file data.** DAT/HSD archives, `.usd`/`.dat` stage and fighter files, and the
  relocation tables are big-endian with 32-bit offsets; `HSD_ArchiveParse` relocates them in
  place into pointers. Natively that needs a loader that byte-swaps per field *and* widens every
  32-bit pointer slot to 64-bit, so file-backed structs (`ftData`, `ItemAttr`, `HSD_JObjDesc`,
  map/coll data...) cannot simply be the file bytes. Each file-backed struct needs a
  description of its fields (type + GC offset) to drive the loader. This is the same table
  the m-ex importer needs (section 5), so build it once.
- **Bitfields**: 1,274 bitfield members in headers. Big-endian PPC allocates bitfields from the
  MSB; x86 from the LSB. Any bitfield that is read as a whole byte/word (flag bytes, the
  `rlwimi` pokes in grbigblue.c, `fp->x2219_b0`-style flags vs raw `u8` reads, unions over
  bitfields) changes meaning. In Rust use explicit flag accessors on a stored integer with
  the PPC bit numbering, never `#[repr(C)]` bitfields.
- **Unions / type punning**: `union { u32; u8[4]; }`, float<->int unions, `PolymorphicDesc`,
  `M2C_FIELD`-style offset casts. Byte order of the punned view flips.
- **Savefile / memcard / netplay / Slippi wire formats** are big-endian by definition; keep
  explicit (de)serialisers.

| src/sysdolphin/baselib/hsd_397E.c | `mfxer/mflr/mfctr/mfdsisr` | crash-screen register reads | under `MWERKS_GEKKO`; return 0 |
| src/Runtime/__init_cpp_exceptions.c | `GetR2` | C++ EH init | not compiled |

So none of the assembly carries game logic on PC. The behaviour that *does* come from the
hardware is in C already: `pc/gameworld/gekko_fp.c` (bit-exact `__frsqrte`, `__fres`, from
Dolphin's tables; and `gk_fmadds`, which models Gekko `fmadds` as
`(float)((double)a*(double)c + (double)b)`, i.e. Dolphin's double-then-float rounding, used by its
sin/cos), and `pc/gameworld/mtx_pc.c`. Port these first and test them in isolation: they are the
float-determinism foundation. Translate `gk_fmadds` literally (f64 multiply, f64 add, `as f32`),
**not** as `f32::mul_add`, which rounds once and would differ from the C build in rare cases.
No contraction anywhere else (Rust does not contract by default; keep it that way).

## 4. Port groups

Include coupling is cyclic at the header level (ft->it 148 TUs, it->ft 74, gr->ft 26, ft->gr 16,
gm includes nearly everything), so the groups are **work order**, not crate boundaries. Plan:
one `melee-types` crate first (every struct, enum and constant, with GC offsets), then the
code in modules of one crate (or crates that depend only on `melee-types` plus lower groups,
with upward calls through function tables/traits where the C already uses callbacks).

| # | group | modules | .c lines | depends on |
|---|---|---|---:|---|
| 0 | types + layout table | all `types.h`/`forward.h` -> `melee-types`; ppc32 record-layout dump -> GC offset table | (headers) | - |
| 1 | runtime, math, HSD core + render | MSL math (`math_ppc.h`), gekko_fp, mtx_pc, mtx44, THPDec, src/sysdolphin/baselib, lb, db, sfx | ~73k | 0 |
| 2 | world: map, camera, stages, effects, HUD | mp, cm, ef, gr, if | ~90k | 1 |
| 3 | fighter engine + common states | ft core, ft/chara/ftCommon, pl | ~76k | 1, 2 (mp, cm, ef) |
| 4 | fighter characters | ft/chara/* except ftCommon | ~80k | 3 |
| 5 | items + trophies + vi | it core, it kinds, ty, vi | ~89k | 3 (items call into fighters heavily) |
| 6 | game modes, menus, port game-side | gm, mn, pc/gameworld/script_game.c, pc/geno, pc/tests | ~107k | everything |

Notes on the cut:
- baselib is kept whole in group 1: its "core" (gobj, jobj, aobj, fobj, archive, memory, random)
  and "render" (pobj, mobj, tobj, dobj, lobj, cobj, particle, generator, psdisp) halves call
  each other constantly, and both sit below the game. If a sixth equal-size group is wanted,
  split them there and move lb into the first half.
- gr is grouped with mp/cm because stages are mostly map/collision/camera code; its calls into
  ft/it are callbacks and can be stubbed while group 2 is tested on stage-only scenes.
- if (HUD) goes with world because it reads player/stock state through pl and gm getters, not
  fighter internals.
- Group 6 is the largest because gm/gmfrontend*.c carries the port's own menus; the frontend
  `.inc` files can be split off to a separate worker.

## 5. GameCube offsets (for the future m-ex importer)

Do not hand-maintain them. The headers already carry offset comments (`/* fp+2C */`, 2,223 of
them) but the authoritative source is the compiler: `clang --target=ppc32-none-eabi
-fsyntax-only -Xclang -fdump-record-layouts-complete <tu>` with the build flags prints every
record's PPC layout (checked: fighter.c dumps 1,397 records; `struct Fighter` starts
`0 gobj, 4 kind, 8 x8_spawnNum, 12 player_id, 16 motion_id ...`). Generate a
`gc_layout` table (struct, field, gc_offset, gc_size, type, bitfield bit range) from that once,
check it into the types crate, and attach it as `#[gc_offset(0x2C)]` attributes or a
`const GC_FIELDS: &[(&str, u32)]` per struct. The same table drives the big-endian file loader
in section 2, the netplay/Slippi serialisers, and the m-ex GC-offset -> native-field map.
